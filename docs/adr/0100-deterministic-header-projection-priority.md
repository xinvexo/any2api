# ADR-0100：确定性的 Header 投影优先级

- 状态：Accepted
- 日期：2026-08-03
- 决策者：maintainer
- 修订：ADR-0065、ADR-0072

## 背景

Provider Header 投影有单值 8 KiB、总计 32 KiB 和 64 个值的固定预算。原实现直接遍历
`HeaderMap`，遇到总字节或数量超限就 `break`。`http::HeaderMap` 明确声明跨名称的迭代顺序任意且可在
版本升级时变化，因此相同白名单和相同输入集合可能因依赖版本选择不同的保留字段。一个靠前遇到的
大值还会阻止后续小字段，即使剩余预算原本足够容纳后者。

简单把 `break` 改成 `continue` 只能修正字节碎片，不能解决优先级由哈希布局决定，也不能说明多个
Provider 字段之间谁应优先。认证、账号和正文一致性字段本来就在投影之外重建，不需要把所有允许字段
都升级为“必保留”；需要的是对可选投影字段建立显式、可测试的保留顺序。

## 决策

1. `project` 的精确名称数组既是白名单也是从高到低的优先级。实现按数组逐名查询 `get_all`，不再
   遍历整张 Map 决定精确字段顺序；重复规则只处理一次。
2. 所有精确规则先于前缀规则。前缀按调用方声明顺序分组；同组名称按规范化小写 Header 名排序。
   一个名称匹配多个前缀时只按最先声明的前缀处理一次。
3. 同名多值使用 `HeaderMap::get_all` 的插入顺序，保留协议允许的多行语义。
4. forbidden、`Connection` 动态点名和单值 8 KiB 上限继续先行过滤。
5. 候选值若使 32 KiB 总预算超限，只跳过该值并继续扫描，允许后续较小值利用剩余空间。达到 64 个
   值后停止，因为任何后续值都不可能再进入结果。
6. Provider 白名单按真实语义重排：协议能力与绑定状态优先于诊断/遥测字段；响应的内容编码、类型和
   请求 ID 优先于额度、边缘节点等辅助元数据。前缀类扩展保持最低优先级。
7. Provider 官方默认身份、ProtocolAdapter 重建字段、最终凭据认证/账号和 Grok 最终模型不经过这个
   可选投影预算，仍由后续合并阶段保证。

## 依据

- [`http::HeaderMap` iteration order](https://docs.rs/http/1.4.2/http/header/struct.HeaderMap.html#iteration-order)
  明确说明除非单独指定，迭代器没有保证顺序，迭代顺序变化不构成 breaking change。
- 同一实现的 `GetAll` 文档保证同名值按插入顺序迭代，适合保留多值 Header 的线协议顺序。

## 后果

- 预算裁剪结果只由 Provider 策略与输入值决定，不再随 HeaderMap 内部布局变化。
- 大型可选字段无法因为偶然先被遍历而挤掉更高优先级的小型协议字段。
- 字节预算出现碎片时仍可容纳后续小字段；安全过滤和总体资源上限不放宽。

## 验证

- 单测覆盖精确优先级不受源插入顺序影响、64 值预算、超大单值、总字节超限后继续接纳小值、前缀组
  顺序与组内字典序，以及 secret/connection-nominated 字段永不投影。
- 实际 Registry 契约继续枚举 Codex、Claude、Grok Driver，验证认证字段不因投影策略进入结果。
