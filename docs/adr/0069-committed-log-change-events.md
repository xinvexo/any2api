# ADR-0069：提交后日志变更事件

- 状态：Accepted
- 日期：2026-07-30
- 修订：2026-07-31
- 决策者：maintainer

## 背景

请求日志原本每秒读取当前页，系统日志在自动刷新开启时每五秒读取当前页。固定轮询即使没有新记录也持续查询 SQLite，还需要客户端 Header 与服务端响应扩展协作，才能避免这些读取本身淹没系统日志。日志的持久化真相仍是 SQLite，管理页面只需要知道已展示的分页快照何时失效，不需要第二份实时日志流。

## 决策

- `RequestTelemetry` 为 RequestLog 和 HttpAccessLog 分别维护一个进程内递增 epoch。它们只是变更通知状态，不是持久化日志、运行态恢复数据或可靠消息队列。
- 后台单 Writer 只在对应 SQLite 批次成功提交后推进 epoch。同一批次无论包含多少需要通知的记录只推进一次；失败写入不得通知。有序系统日志清理和两类保留删除只有在确实删除记录后推进对应 epoch。
- 精确的 `GET /api/admin/system-logs` 仍按统一 HttpAccessLog 规则决定是否持久化和展示，但 Server 在请求捕获边界把它标记为不推进 `system_logs_changed`。只包含这类自读记录的批次成功提交后不修改系统日志 epoch；混合批次只要包含其他 HttpAccessLog，仍推进一次。该服务端语义同时覆盖首次加载、自动刷新、手动刷新和失败响应，不接受客户端 Header 覆盖。
- Server 提供已认证管理端点 `GET /api/admin/log-events`，使用 Server-Sent Events 发送 `request_logs_changed` 与 `system_logs_changed`。事件数据只包含对应 epoch，不包含日志、Attempt、Secret、请求或响应正文；响应明确禁用反向代理缓冲，避免事件被攒批后才交付浏览器。
- 新连接先发送两个当前 epoch；随后只发送变化。SSE keepalive 仅维持连接，不表示数据改变。epoch 和事件不持久化、不跨进程恢复、不使用 `Last-Event-ID` 回放；浏览器原生重连后收到当前 epoch并重新查询当前页，天然覆盖断线期间的合并变化。进程进入 draining 时主动结束这条非关键通知流，避免空闲管理连接延长更新或停机；新进程就绪后浏览器继续原生重连。
- 请求日志页面始终订阅请求日志事件；系统日志自动刷新开关只控制是否订阅系统日志事件。收到事件后 TanStack Query 使当前分页失效并重新读取，首次加载与手动刷新继续使用普通分页 API。
- 成功建立的日志 SSE 响应由服务端标记为不写 HttpAccessLog，避免长连接 keepalive 或断开形成噪音。该能力不由客户端 Header 控制；认证失败和其他管理请求仍执行正常审计规则。
- 删除固定一秒/五秒轮询与 `X-Any2API-Log-Refresh`，不引入 WebSocket、日志正文推送、事件历史表或后台回放。

## 后果

- 没有日志变化时不会产生分页查询；写入批次完成后页面才读取，因此不会出现通知先于 SQLite 可见性的竞态。
- 多条日志可以合并为一次刷新，实时界面不会把每条记录扩展为独立网络请求。
- 系统日志列表读取不会因记录自身、推进 epoch、SSE 失效和再次读取而形成自激循环；读取本身仍保留远程管理审计价值，并在后续真实变化或手动读取时可见。
- SSE 不是可靠事件消费接口。进程重启或网络中断期间的中间 epoch 可以丢失，但重连后的当前 epoch 会使页面读取 SQLite 真相，因此管理界面不依赖事件历史正确恢复。

## 验证

- Runtime 测试验证成功提交、清理和保留删除推进正确 epoch，失败写入不推进。
- Runtime 测试验证系统日志列表自读记录成功持久化但不推进 epoch，后续需要通知的记录仍正常推进。
- Server 契约测试验证管理鉴权、SSE 事件名与初始 epoch、成功通知流不会写入 HttpAccessLog，以及系统日志列表读取不会产生新的 `system_logs_changed`。
- Web 测试验证收到对应事件后只重新读取当前页，系统日志开关会建立或关闭订阅，且不存在固定轮询 Header。
